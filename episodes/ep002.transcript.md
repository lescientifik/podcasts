# Closed-loop d'évaluation et d'optimisation pour un agent PydanticAI

En mars 2026, Andrej Karpathy a publié AutoResearch, un petit système qui a fait beaucoup de bruit. L'idée tient en trois lignes : un agent autonome modifie un fichier d'entraînement, mesure une métrique scalaire, garde la modification si la métrique progresse, et recommence. En deux jours, sept cents expériences plus tard, ce dispositif a trouvé une vingtaine d'améliorations qui cumulent un speed-up de onze pour cent sur le pipeline nanochat — c'est-à-dire sur du code que Karpathy lui-même avait déjà optimisé. Tobias Lütke, le CEO de Shopify, a reproduit l'exercice à sa façon : trente-sept expériences nocturnes, dix-neuf pour cent de performance gagnée sur un modèle de huit cents millions de paramètres comparé à son baseline d'un milliard six cents millions. Le message de Karpathy est limpide : pour profiter pleinement des outils disponibles aujourd'hui, il faut se retirer soi-même du chemin critique. L'humain, à itérer à la main, devient le goulot d'étranglement.

La question qu'on va se poser dans cet épisode, c'est la suivante : peut-on transposer cette idée à un agent LLM, c'est-à-dire à un système où le signal de qualité n'est plus un nombre propre comme la perplexité de validation, mais un jugement de modèle, fragile, biaisé, non-déterministe ? Peut-on construire une closed-loop dans laquelle Claude Code orchestre l'exécution d'un agent PydanticAI, capture sa trajectoire complète via OpenTelemetry, fait juger ses sorties par un autre LLM via Pydantic Evals, et propose itérativement des mutations du prompt et du toolset pour améliorer ses scores ? Et surtout, qu'est-ce qui se transpose proprement, qu'est-ce qui casse, et quelles sont les mitigations concrètes pour éviter que la boucle se mette à dériver ? On va prendre le temps. D'abord la théorie — pourquoi les evals one-shot s'effondrent sur les agents, ce qu'on garde d'AutoResearch, ce qui ne se copie-colle pas. Ensuite l'architecture concrète, brique par brique. Et enfin, les pièges, parce que sans eux ce podcast ne serait qu'un publi-reportage outillage.

Commençons par poser le décor. Pourquoi a-t-on besoin d'une boucle fermée pour un agent LLM ? La première raison, c'est que les évaluations one-shot — un input, un output, un score — s'effondrent dès qu'on bascule sur un agent. Anthropic le formule clairement dans son article Demystifying evals for AI agents : les capacités qui rendent les agents utiles sont précisément celles qui les rendent plus difficiles à évaluer. Trois raisons à cela. D'abord, le multi-turn et l'usage de tools. Un agent enchaîne des appels de modèle et de tools, parfois des dizaines, parfois récursivement. La donnée brute à évaluer n'est plus une chaîne de caractères mais un arbre d'événements. Ensuite, le non-déterminisme structurel : deux runs sur la même tâche peuvent réussir par des chemins différents. Anthropic recommande explicitement de juger ce que l'agent a produit, et non le chemin qu'il a pris, et propose deux métriques pour quantifier la variance — pass-at-k, c'est-à-dire au moins un succès sur k tentatives, et pass-puissance-k, c'est-à-dire k succès consécutifs. Ces deux métriques divergent fortement à mesure que k augmente, ce qui est précisément le signal qu'on est face à un système instable. Enfin, le succès partiel existe : un agent peut réussir quatre-vingts pour cent d'une tâche puis dérailler sur la dernière étape, et un score binaire écrase cette information.

Ce qui suit logiquement, c'est que l'objet à évaluer n'est plus une sortie, mais une trajectoire. Une trajectoire d'agent, comme le rappellent LangChain et Braintrust, c'est un arbre de spans, où chaque span représente une étape — un appel de modèle, une invocation de tool, un dispatch vers un sous-agent, une récupération depuis une base de connaissances. Évaluer un agent suppose donc de capturer puis de raisonner sur cet arbre, pas seulement sur son output terminal. Les frameworks d'observabilité qu'on connaît — Phoenix d'Arize, Braintrust, Langfuse — convergent tous sur ce point : la trajectory evaluation, c'est juger la séquence des tool calls, leur ordre, leur pertinence, leur idempotence éventuelle. On distingue généralement trois modes de comparaison : le mode strict, où l'on attend les mêmes tool calls dans le même ordre avec les mêmes arguments ; le mode subset, qui interdit simplement les tool calls superflus par rapport à une référence ; et le mode unordered, qui demande seulement le bon ensemble de tool calls, sans contrainte d'ordre. Anthropic met d'ailleurs en garde contre la rigidité du mode strict : noter une séquence très spécifique de tool calls dans le bon ordre, c'est exclure les solutions valides imprévues. La trajectoire sert plus à diagnostiquer qu'à noter au sens strict.

Voilà pour la motivation. Passons maintenant au cadre conceptuel emprunté à Karpathy, parce que c'est là que se joue l'essentiel de l'angle théorique. AutoResearch tient sur trois fichiers et trois principes. Le premier principe, c'est l'editable asset : un seul fichier, train.py, que l'agent peut modifier librement. Architecture, hyperparamètres, optimizer, batch size — tout est négociable, mais dans un périmètre étroit, moins de six cent trente lignes pour tenir dans le contexte. Le reste, prepare.py, les métriques, les données, est gelé. Le deuxième principe, c'est le scalar metric : val-bpb, validation bits per byte, qui a la propriété d'être indépendant de la taille de vocabulaire, monotone, peu bruité, calculé par du code immuable. Lower is better, et un seul nombre par expérience. Le troisième principe, c'est le time-boxed cycle : cinq minutes wall-clock, point. Ça donne environ douze expériences à l'heure, environ cent par nuit. Cette time-box force la comparabilité et empêche un run pathologique de monopoliser le GPU. Le slogan de Karpathy le résume : one GPU, one file, one metric.

Maintenant, qu'est-ce qui se transpose proprement à un agent LLM ? Réponse courte : la forme. Train.py devient le couple système prompt plus toolset, descriptions et signatures incluses. Prepare.py, qui est gelé, devient le Dataset Pydantic Evals avec ses rubrics et ses evaluators, au moins les déterministes. Le program.md de Karpathy, c'est-à-dire les instructions que reçoit l'agent qui modifie le code, devient le prompt système de Claude Code en rôle d'orchestrateur ou d'évaluateur. La boucle keep-or-discard via git devient un manifest de runs versionné, en git ou en YAML ou en JSON, avec ses scores. Et le cycle de cinq minutes devient un budget par itération, exprimé en nombre de cas d'évaluation multiplié par le nombre de runs pour gérer la variance, borné en latence et en dollars.

Mais ce qui ne se transpose pas, c'est la substance. Et c'est crucial. Premier point qui casse : le scalar metric n'est plus propre. Val-bpb est calculé par du code, déterministe, indépendant du vocabulaire. Un score de juge LLM est non-déterministe, biaisé — biais positionnel, biais de longueur, self-preference — et lui-même un agent qui peut se faire tromper. La documentation de Pydantic prévient explicitement : un même output peut recevoir des scores différents d'un run à l'autre. Deuxième point : l'agent évalué est lui-même non-déterministe à l'exécution. AutoResearch peut comparer deux runs de train.py parce que l'entraînement est suffisamment stable. Un agent LLM peut emprunter deux trajectoires totalement différentes pour le même input. Il faut donc moyenner sur plusieurs runs, ce que pass-at-k impose, et ça multiplie le coût.

Troisième point, et c'est probablement le plus profond : la loi de Goodhart explose plus vite. Karpathy lui-même reconnaît la limite de sa méthode : elle ne fonctionne que là où l'évaluation se réduit à des métriques numériques. Les domaines de recherche qui touchent à l'alignement, à l'interprétabilité ou au jugement subjectif restent hors de portée d'une telle automatisation. Quand le métrique est lui-même un LLM, le mutateur peut apprendre à plaire au juge plutôt qu'à résoudre la tâche — c'est précisément ce que Lilian Weng documente dans son long article sur le reward hacking. Quatrième point : le coût n'est pas symétrique. Un cycle de cinq minutes sur GPU, c'est un coût bien identifié. Un cycle d'eval LLM, c'est le nombre de cas multiplié par le nombre de répétitions, multiplié par les appels de l'agent et les appels du juge. On dépasse vite les budgets raisonnables. Cinquième point : l'eval set vieillit. AutoResearch a une métrique gravée dans le marbre. Une rubric d'évaluation, au contraire, doit être révisée à mesure que l'agent progresse, sinon on overfitte la rubric.

À retenir, donc : on garde la forme — boucle autonome, time-box, manifest versionné, scalar metric d'arbitrage final — et on muscle la substance, par du multi-métriques, du multi-judges, un holdout, une calibration humaine périodique. C'est exactement le programme qu'on va dérouler dans les sections suivantes.

Passons maintenant à l'architecture cible. Imaginez le diagramme suivant. Au centre, Claude Code orchestrateur. Il fait trois choses en parallèle : il lance des runs de l'agent, il lit les traces produites, et il propose des mutations du prompt et des tools. L'agent PydanticAI lui-même, qui est composé d'un système prompt et d'un FunctionToolset, émet des spans OpenTelemetry à chaque step — agent, model call, tool call. Ces spans atterrissent dans un trace store local, qui peut être Jaeger, Phoenix, Tempo, ou simplement un fichier JSON exporté. L'output structuré de l'agent passe ensuite par le Dataset Pydantic Evals, où des cases sont confrontées à des evaluators — un mélange de LLMJudge et d'evaluators custom — et produisent un EvaluationReport. Cet ensemble — la trajectoire et le rapport — est lu par un sous-agent Claude Code en rôle d'évaluateur LLM-as-judge sur trajectoire plus output. Le tout est sérialisé dans un manifest YAML par run, qui contient la version du prompt, la version des tools, les scores, le path des traces, et le diff par rapport au run précédent. Ce manifest alimente la phase de réflexion et de proposition de mutation, qui boucle vers l'itération suivante.

On distingue idéalement quatre sous-agents Claude Code, avec des prompts système distincts. Le premier, le runner, reçoit la version courante du couple prompt-tools, exécute l'agent PydanticAI sur le Dataset Pydantic Evals, sauvegarde les inputs et les outputs, et vérifie que les traces OpenTelemetry sont bien écrites. Le deuxième, le trace analyzer, lit les spans bruts — exportés en JSON ou requêtés depuis le collector — et produit un résumé structuré par cas : nombre de tool calls, ordre, arguments, retours, erreurs, durées. Le troisième, le judge, applique la rubric multi-critères. Idéalement, le modèle utilisé par le judge est différent du modèle de l'agent sous test, ce qui atténue la self-preference. Il produit un score par critère plus un raisonnement explicite. Le quatrième, le mutator, reçoit deux choses : d'un côté l'historique des runs avec leurs scores et leurs diffs, de l'autre les analyses de trajectoire et les rapports du juge. Il propose alors une seule mutation pour le prochain run, justifiée. Une seule, pour préserver l'attribution de l'amélioration. L'option d'un agent unique qui fait tout marche techniquement, mais elle brouille les rôles et rend le log d'expériences illisible. La séparation est préférable.

Concrètement, chaque run produit un dossier nommé d'après son identifiant, par exemple run zéro zéro quarante-deux. Dedans on trouve un manifest YAML qui contient la version du prompt, la version des tools, l'identifiant du dataset et les scores. On y trouve aussi un snapshot exact du prompt en texte, un snapshot des tools en Python — ou un hash avec une référence à un store partagé. Il y a un dossier d'outputs avec un fichier par cas, un dossier de traces avec les spans OTel, un fichier judge-report en JSON qui contient les sorties du LLMJudge et leurs raisonnements, des notes d'évaluateur écrites par Claude Code en synthèse réflexive, et un diff Markdown qui décrit ce qui a changé par rapport au run parent. Ce manifest YAML, c'est l'analogue exact du commit git d'AutoResearch. Il rend les comparaisons triviales et permet d'écarter rapidement les branches d'optimisation infructueuses.

Maintenant, parlons de l'espace d'optimisation. Et ici, c'est la spécificité forte de notre approche par rapport à un GEPA classique, qui se concentre uniquement sur les instructions des signatures DSPy. Pour un agent PydanticAI, le tissu manipulable est beaucoup plus large. Il y a évidemment le système prompt, mais il y a aussi les descriptions de tools, les signatures elles-mêmes, et la composition des toolsets. On va prendre chaque axe séparément.

Le système prompt d'abord. Les variations canoniques qu'on peut explorer, ce sont d'abord des rewrites globaux : ton, persona, longueur, structure — sections numérotées versus prose continue. C'est ensuite l'ajout ou le retrait d'exemples few-shot, en faisant attention au coût en tokens et au risque d'overfitting au format des exemples. Ce sont des contraintes explicites qu'on ajoute, du genre : avant tout tool call, formule une hypothèse ; ou bien, si la réponse fait moins de N caractères, vérifie avec le tool X. C'est aussi la décomposition : injecter une chain-of-thought structurée versus laisser l'agent libre de raisonner. Ce sont enfin les méta-instructions sur l'utilisation des tools : un ordre préférentiel, un tool de fallback désigné, une politique de gestion d'erreur.

Les descriptions de tools, ensuite. Et ici, beaucoup de praticiens sous-estiment le levier. PydanticAI dérive automatiquement la description d'un tool de sa docstring, et les descriptions de paramètres viennent du même endroit, dans le style Google, Sphinx ou NumPy détecté automatiquement. On peut aussi forcer une description en passant explicitement le paramètre description au constructeur Tool, ou bien injecter dynamiquement via le hook prepare. Les variations à explorer ici, c'est d'abord la verbosity. Description ultra-courte versus détaillée. Trop courte, l'agent ne sait pas quand l'appeler. Trop longue, c'est du token bloat et du bruit qui dilue les autres tools. Il y a ensuite les exemples in-docstring : un mini-exemple d'invocation peut radicalement améliorer le taux d'appel correct. Il y a le cas d'usage explicite, formulé du genre : utilise ceci quand l'utilisateur demande X, mais pas quand Y. Cette désambiguïsation marche souvent mieux qu'une longue description neutre. Il y a l'ordre des tools dans le toolset : la position dans le contexte influe, parce que les LLMs eux-mêmes ont un biais positionnel. Et il y a le nommage : search-documents versus retrieve-relevant-docs versus query-knowledge-base. L'écart de comportement entre ces trois noms, sur le même tool, n'est pas négligeable.

Au-delà du nom et de la description, la signature elle-même est un levier. Les types d'abord : un paramètre déclaré comme entier versus un Literal contenant trois valeurs autorisées versus un enum Pydantic — contraindre via les types réduit drastiquement les appels invalides. Les valeurs par défaut ensuite : un paramètre avec une default value est moins « obligatoire » dans la perception du LLM, ce qui peut être un bug ou une feature selon le cas. Le caractère required versus optional : surcharger un tool avec beaucoup de paramètres optionnels brouille l'appel. Et la structure imbriquée : un seul tool à huit paramètres versus deux tools à quatre paramètres après split. PydanticAI gère bien des BaseModel imbriqués comme paramètres, mais cela alourdit le schéma JSON présenté au modèle, ce qui peut nuire à la qualité de l'appel.

Mais le levier le plus puissant et le plus négligé, c'est la composition. PydanticAI offre une API riche qu'il faut connaître. Le FunctionToolset, c'est le conteneur de tools, avec ses méthodes add-function et add-tool, ses décorateurs at-toolset-tool et at-toolset-tool-plain. Le CombinedToolset permet de fusionner plusieurs toolsets. Le FilteredToolset applique un filtre dynamique selon le contexte, ce qui est utile si on veut montrer un sous-ensemble de tools selon l'étape de la conversation. Les PrefixedToolset et RenamedToolset permettent du namespacing et du renommage. Et le PreparedToolset modifie la liste des ToolDefinition avant chaque step, ce qui ouvre la porte à des descriptions dynamiques contextuelles. Les mutations typiques qu'on peut imaginer ici, c'est ajouter un tool helper qui n'existait pas — par exemple un validate-format — parce que le juge a noté plusieurs sorties mal formattées. C'est retirer un tool jamais appelé ou systématiquement mal appelé. C'est fusionner deux tools redondants, par exemple search-by-id et search-by-name en un seul search qui accepte une union de string ou d'entier. C'est splitter un tool trop générique du genre do-thing avec un paramètre action et un paramètre payload, en plusieurs tools spécialisés et typés. Une règle d'hygiène, inspirée du A-B testing : une seule mutation par run quand on est en phase de diagnostic, plusieurs quand on accepte de perdre l'attribution. Karpathy édite librement train.py, mais il a un métrique propre et beaucoup d'expériences. Nous, en LLM eval, le bruit est tel qu'isoler la cause d'un gain est précieux.

Passons maintenant à Pydantic Evals comme socle de la mesure. Les concepts sont au nombre de trois. Le premier, c'est le Case : une unité de test, qui possède un nom, des inputs, optionnellement un expected-output, des métadonnées libres — par exemple un champ difficulty, un tag, une catégorie — et optionnellement des evaluators spécifiques au cas. Le deuxième concept, c'est le Dataset : une collection de cases plus des evaluators globaux plus un nom. Le troisième, c'est l'Evaluator : un composant qui produit un score, qui peut renvoyer un scalaire, un objet EvaluationReason avec une valeur et une raison textuelle, ou un dictionnaire de plusieurs résultats nommés. Concrètement, on définit une dataclass Case avec un champ inputs, un champ expected-output et un champ metadata. On l'agrège dans un Dataset où on déclare aussi la liste des evaluators à appliquer. Et on appelle une méthode evaluate-sync qui prend la fonction de l'agent à tester et qui renvoie un EvaluationReport avec un détail par case et des agrégats par evaluator.

Le LLMJudge mérite qu'on s'y attarde. Ses paramètres clés sont les suivants. La rubric, c'est la consigne textuelle. Pydantic insiste : il faut être spécifique. On préfère une rubric formulée comme « la réponse répond directement à la question sans hallucination » à un vague « la réponse est bonne ». Il y a le flag include-input, qui par défaut est faux et qui injecte l'input original dans le prompt du juge — ce flag est indispensable pour les cas RAG ou les cas agent. Il y a include-expected-output pour les comparaisons golden. Il y a le model, qu'on choisit explicitement, par exemple openai-gpt-5-mini pour du cheap, ou anthropic-claude-sonnet-4-6 pour de la qualité. Il y a model-settings, où on recommande de mettre la température à zéro pour la stabilité. Et il y a les modes assertion ou score, qui définissent si la sortie est un booléen pass-fail, un score continu entre zéro et un, ou les deux avec des noms personnalisés.

Quatre best practices documentées. D'abord, des rubrics multi-points plutôt qu'une seule consigne floue. Ensuite, plusieurs juges sur des dimensions différentes — factualité, ton, format — plutôt qu'un méga-juge qui fait tout. Puis, combiner avec des checks déterministes : IsInstance, Contains, Equals — ces checks s'exécutent en premier et permettent un fail-fast avant les coûteux appels LLM. Et enfin, température zéro côté juge, systématiquement. Pour aller au-delà des évaluateurs intégrés, on étend la classe Evaluator. On définit par exemple un ToolCallCountEvaluator qui prend en paramètre un max-calls — disons cinq — et qui dans sa méthode evaluate lit le nombre de tool calls dans le contexte de métadonnées, vérifie qu'il est inférieur à la limite, et renvoie un EvaluationReason avec une valeur booléenne et une raison textuelle qui dit par exemple « trois tool calls, limite à cinq ». Un même evaluator peut renvoyer un dictionnaire pour produire plusieurs résultats nommés — accuracy, efficiency, format-ok — chacun avec sa raison, qui apparaîtront séparément dans le rapport quand on demande include-reasons à l'impression.

Le rapport final, c'est ce que renvoie evaluate-sync : un EvaluationReport qui contient le détail par case et les agrégats par evaluator. La méthode print produit un tableau lisible. Pour la closed-loop, on l'écrit aussi en JSON pour que le subagent mutator le re-parse au prochain tour. Petite parenthèse importante : l'intégration Logfire de Pydantic est volontairement écartée ici, parce qu'elle est payante. On capture les events Pydantic Evals via OpenTelemetry comme tout le reste, ce qui nous amène à la prochaine section.

OpenTelemetry, donc, ou OTel pour les intimes. Pourquoi OTel et pas un wrapper maison ? Trois raisons. Premièrement, c'est un standard ouvert. L'OTel SDK existe en Python, et il y a plusieurs collectors open-source qu'on peut self-héberger : Jaeger, Tempo de Grafana, Phoenix d'Arize, ClickHouse via SigNoz. Pas de lock-in. Deuxièmement, PydanticAI émet déjà des spans OTel structurés dès qu'on active l'instrumentation. Pas besoin de coder soi-même la capture. Troisièmement, la sémantique GenAI est conventionnelle : les versions récentes des conventions stockent les messages dans gen-ai-input-messages, gen-ai-output-messages, gen-ai-system-instructions. C'est rétro-compatible avec d'autres backends GenAI, donc on peut switcher de backend d'observabilité sans tout récrire.

Côté activation dans PydanticAI, deux modes existent. Soit on instancie l'Agent en passant le flag instrument à vrai au cas par cas, soit on appelle une méthode globale Agent.instrument-all avant tout appel, qui instrumentent tous les agents du processus. On peut aussi utiliser l'instrumentation OpenInference, qui ajoute des conventions sémantiques AI en plus des conventions GenAI standards. Quelques paramètres notables d'InstrumentationSettings : include-content, qui par défaut est vrai et embarque les prompts et les completions dans les events ; version, qu'on peut régler de un à cinq, et où on préfère cinq pour la gestion correcte des deferrals ; event-mode, qui peut être attributes ou logs, mais seulement dans la version un de la convention ; et tracer-provider et meter-provider, qu'on peut pointer vers son propre SDK custom au lieu du provider global.

Concrètement, à quoi ressemble la structure d'un span hiérarchique ? On a un span racine qui s'appelle agent-run. Sous ce span, on trouve des spans enfants. Le premier est typiquement un chat sur le modèle — c'est l'appel de modèle numéro un — qui a comme attributs gen-ai-input-messages, gen-ai-output-messages, et gen-ai-usage-input-tokens avec un compteur de tokens. Ensuite vient un span tool-call, par exemple search-documents, avec des attributs tool-name, tool-arguments avec la query, et tool-result avec le résultat. Puis un autre chat sur le modèle, l'appel numéro deux. Et un autre tool-call, par exemple send-email. C'est cette arborescence que le subagent trace analyzer doit lire.

Concrètement, il a trois options. L'option A, c'est OTLP vers Jaeger ou Tempo en local, lancés via Docker Compose, sur le port seize-mille-six-cent-quatre-vingt-six pour l'UI et le port quatre-mille-trois-cent-dix-sept pour OTLP en gRPC. Le trace-id du run est sauvegardé dans le manifest, et le subagent interroge l'API Jaeger pour récupérer les spans correspondants. L'option B, c'est exporter directement vers un fichier JSON local, via un SpanExporter custom ou bien via le ConsoleSpanExporter standard redirigé vers un fichier. C'est plus simple, parfait pour la CI et pour un MVP. L'option C, c'est Phoenix en local, qui écoute par défaut sur le port six-mille-six. Phoenix offre une UI dédiée aux traces LLM, avec une lecture des spans depuis le SDK Python via l'API Phoenix.

Le snippet de code minimal pour activer l'export local, je vais le décrire en prose. On importe trace depuis opentelemetry, TracerProvider depuis opentelemetry-sdk-trace, BatchSpanProcessor depuis opentelemetry-sdk-trace-export, et OTLPSpanExporter depuis opentelemetry-exporter-otlp-proto-http-trace-exporter. On instancie un TracerProvider, on crée un OTLPSpanExporter qui pointe vers l'endpoint HTTP local sur le port quatre-mille-trois-cent-dix-huit avec le path slash v-un slash traces. On wrap l'exporter dans un BatchSpanProcessor qu'on ajoute au provider. On installe ce provider comme provider global via trace.set-tracer-provider. Et on appelle Agent.instrument-all. À partir de là, tous les agents PydanticAI émettent leurs spans vers le collector. Pour un setup encore plus minimaliste, on peut utiliser le ConsoleSpanExporter et un parseur de logs JSON. Tant qu'on a tool-name, tool-arguments, tool-result, parent-span-id, start-time et end-time, on a tout ce qu'il faut pour reconstruire la trajectoire.

Comment Claude Code lit ces traces ? Le subagent trace analyzer reçoit en input le trace-id ou le path JSON et produit, par cas du dataset, un résumé canonique en YAML. Ce résumé contient le nom du cas, par exemple refund-request, la durée totale en millisecondes, le nombre total de tool calls, la séquence des tool calls — chacune avec son nom, ses arguments, un flag ok, sa durée, et éventuellement une erreur — l'output final, et une liste de flags, par exemple « tool error not recovered » ou « duplicate search-documents call avoided ». Ce résumé devient l'input principal du subagent judge et du subagent mutator. Sans cette étape, la rubric LLMJudge ne juge que l'output final. Avec, elle juge le processus. C'est l'apport central de la trajectoire.

On arrive maintenant à la boucle d'optimisation pilotée par Claude Code, c'est-à-dire le workflow complet d'une itération. Étape un : lire le manifest du run précédent — disons run-zéro-zéro-quarante-et-un — sa trace, et son judge-report. Étape deux : le mutator génère une proposition de mutation argumentée, par exemple « ajouter un exemple in-docstring sur send-email parce que le judge a flaggé deux cas de mauvais formatage ». Étape trois : appliquer la mutation, c'est-à-dire produire un nouveau prompt-txt et un nouveau tools-py pour le run-zéro-zéro-quarante-deux. Étape quatre : le runner lance le Dataset Pydantic Evals contre la nouvelle version, avec idéalement trois runs par cas pour la stabilité, et OpenTelemetry actif. Étape cinq : le trace analyzer produit les résumés de trajectoire. Étape six : le judge, qui combine LLMJudge multi-rubrics et evaluators custom, produit des scores par dimension. Étape sept : on écrit le manifest du run-zéro-zéro-quarante-deux avec les scores agrégés, le diff, et le raisonnement. Étape huit : on décide — keep ou discard. Étape neuf : on itère.

Le prompt du subagent évaluateur, c'est-à-dire la rubric multi-critères, mérite qu'on s'y arrête. Une rubric monolithique du genre « score this output from one to ten » est l'erreur classique. On préfère décomposer. Prenez un agent de support client. La rubric va dire : tu juges la sortie d'un agent de support client, évalue indépendamment chaque critère, sur une échelle de zéro à un, avec justification. Premier critère, intent-accuracy : l'intention détectée correspond-elle à la demande de l'utilisateur ? Deuxième critère, slot-filling : tous les slots requis sont-ils extraits correctement ? Troisième critère, tone : le ton est-il professionnel et empathique ? Quatrième critère, efficiency : le nombre de tool calls est-il raisonnable, c'est-à-dire inférieur ou égal à cinq ? Cinquième critère, error-handling : les erreurs de tools sont-elles récupérées proprement ? Et la rubric conclut : renvoie un JSON avec pour chaque critère un score et une raison. N'attribue pas de score global. Pénalise la verbosité inutile.

Trois principes derrière cette rubric. D'abord, on demande explicitement la justification, qui sera tracée dans le champ reason de l'EvaluationReason. Ensuite, on pénalise explicitement la verbosité dans la rubric — c'est une contre-mesure documentée au verbosity bias des juges LLM. Enfin, on ne demande pas de score global au juge. L'agrégation est faite par l'orchestrateur, pas par le juge, pour éviter que le juge synthétise selon ses propres priors implicites.

Concernant la stratégie de sélection de mutations, plusieurs régimes sont possibles, du plus simple au plus sophistiqué. Le régime greedy : on accepte la mutation si le score agrégé du nouveau run est supérieur au précédent. C'est simple, mais myope. Le régime greedy avec garde-fou regression : on rejette toute mutation qui dégrade un critère essentiel, par exemple intent-accuracy, même si la moyenne générale progresse. C'est exactement l'idée d'Anthropic des regression evals à pass-rate quasi-cent-pour-cent qui protègent du backsliding. Le régime Pareto : on garde une frontière de candidats non-dominés sur les K critères. C'est inspiré directement de GEPA, c'est plus robuste contre l'optimisation locale, mais c'est plus coûteux à gérer. Le régime bandit, ou UCB pour Upper Confidence Bound : on sur-itère sur les branches d'optimisation prometteuses, ce qui est pertinent si on garde plusieurs lignées en parallèle, comme ce que fait GEPA via le merge de variantes. Pour un MVP, je recommande le régime greedy plus regression guard. C'est suffisant et lisible. Le Pareto, on l'ajoute si on a du budget et si on remarque que l'optimisation locale est un problème en pratique.

Critères d'arrêt de la boucle, trois grandes familles. Le plateau : pas d'amélioration au-delà d'un seuil — par exemple plus d'un point sur le critère cible — sur N itérations consécutives. Le budget : un nombre maximal d'itérations, ou un coût maximal en dollars, ou un wall-time maximal. C'est l'analogue de la time-box AutoResearch, mais à l'échelle de la boucle entière, pas d'une seule itération. La saturation : score cible quasi-cent pour cent. Anthropic rappelle qu'à ce moment-là, il faut construire un eval set plus dur, parce qu'on est saturé.

Le manifest YAML mérite qu'on en décrive un exemple concret. Pour le run-zéro-zéro-quarante-deux, on a un champ run-id, un champ parent-run-id qui pointe vers run-zéro-zéro-quarante-et-un, un timestamp, une section mutation qui décrit le type — par exemple tool-description — le tool concerné — par exemple send-email — la description de la mutation — par exemple « added concrete usage example in docstring » — et un path vers le diff Markdown. On a aussi un prompt-hash et un tools-hash en SHA-256. Un dataset-id, par exemple support-intents-v3. Un nombre de runs par cas, par exemple trois. Une section scores avec, pour chaque critère, une moyenne et une variance — par exemple intent-accuracy à zéro virgule quatre-vingt-douze de moyenne et zéro virgule zéro un de variance, slot-filling à zéro virgule quatre-vingt-cinq de moyenne, et ainsi de suite. Un agregate global, par exemple zéro virgule huit-cent-soixante-huit. Le parent-aggregate. Un verdict KEEP ou DISCARD. La liste des trace-paths. Et un champ notes en texte libre, du genre « mutation acceptée, gain modeste mais cohérent, error-handling reste le critère le plus faible, c'est la cible suivante ». Cette pierre angulaire qu'est le manifest permet à Claude Code de lire son propre passé sans avoir à re-parser des traces brutes à chaque itération.

On arrive maintenant à la section qui sauve le podcast d'être un publi-reportage outillage : les pièges et les anti-patterns. Premier piège, le plus profond : le reward hacking et la loi de Goodhart. Quand une mesure devient une cible, elle cesse d'être une bonne mesure. Lilian Weng documente longuement comment l'optimisation contre un proxy LLM-judge dérive : utiliser des LLMs comme graders est un proxy imparfait pour la récompense oracle, et peut introduire des biais qui mènent à du reward hacking en exploitant ces graders. Mitigations pratiques : plusieurs juges sur des dimensions disjointes, où la corrélation des dérives entre juges devient elle-même un signal d'alerte. Un holdout dataset que le mutateur ne voit jamais, et qu'on évalue tous les K runs ; si le score sur le train monte mais que le score sur le holdout chute, on est en plein overfitting et on doit reculer. Des checks déterministes en pré-filtre — format, schémas, présence d'éléments factuels — qui sont incorruptibles parce qu'exécutés par du code. Et un périmètre de mutation borné : un mutateur libre de tout réécrire trouvera plus vite des hacks qu'un mutateur contraint à des transformations canoniques.

Deuxième piège : les biais du juge, qu'il faut traiter comme une checklist. Le biais positionnel : le juge préfère systématiquement la première option, ou alors la deuxième selon le modèle utilisé. Mitigation : faire un pairwise twin-call avec un swap, et ne valider la décision que si elle est stable. Le biais de verbosity : le juge donne un score haut aux longues réponses indépendamment de leur qualité. Mitigation : pénaliser explicitement la verbosité dans la rubric, et contraindre la longueur côté agent. Le biais de self-preference : le juge préfère les sorties de modèles qui lui sont familiers, c'est-à-dire à faible perplexité pour lui. Mitigation : utiliser un juge d'un autre vendeur que l'agent sous test. Le biais d'authority : le juge crédibilise les citations même fabriquées. Mitigation : reference-guided eval, c'est-à-dire passer les sources réelles au juge pour qu'il vérifie. Le biais de moderation : le juge surnote les refus prudents. Mitigation : calibration humaine sur les cas sensibles. Recommandation transverse : calibrer périodiquement le juge contre un golden labellé par un humain. Pydantic insiste explicitement sur ce point — valider contre des labels humains.

Troisième piège, l'erreur miroir d'AutoResearch : la métrique scalaire fragile. On force l'agrégation en un seul nombre, alors que les critères sont tirés dans des directions différentes. Symptôme typique : un run gagne un point sur l'agrégat parce qu'il a gagné cinq points sur la verbosity — réduction de longueur — tout en perdant trois points sur la factualité. Réponse : suivre toutes les dimensions et ne décider qu'avec une règle multicritère explicite, pas avec une moyenne aveugle.

Quatrième piège : l'instabilité de l'optimisation prompt. Un même prompt avec un même input peut donner deux scores différents. Doug Turnbull a une formule juste : les hard negatives — ces dix à vingt pour cent de cas difficiles où humains et juges divergent — sont la zone où tout se joue. Mitigations : plusieurs runs par case, avec un minimum de trois, et reporter mean et variance. Température zéro côté juge, systématiquement. Et avoir des cas seed, c'est-à-dire des cases déterministes peu ambiguës qui doivent renvoyer le même score à chaque run. Si même là le score bouge, c'est qu'il y a un bug dans le pipeline.

Cinquième piège : l'overfitting au dataset d'eval. C'est le risque dont parle DeepEval et Evidently AI : on optimise jusqu'à parfait sur trente cas, on déploie en production, et on découvre que le trente-et-unième ne marche pas. Mitigations : un split train-validation-holdout des cases, typiquement soixante-vingt-vingt. Une croissance du dataset, où le mutateur écrit des cas synthétiques adversariaux à partir des modes de défaillance observés, où l'humain les valide, et où ils entrent ensuite dans le dataset. Et une diversité explicite, c'est-à-dire un tagging par catégorie dans le metadata du Case, et un reporting par catégorie pour repérer une régression locale qui serait masquée par une moyenne globale.

Sixième piège : les faux positifs sur petits datasets. Anthropic recommande vingt à cinquante cas pour démarrer, mais avec un caveat statistique implicite : un gain de deux points sur trente cases peut tout à fait être du bruit pur. Mitigations : un bootstrap sur les scores pour produire un intervalle de confiance avant d'accepter une mutation. Un seuil minimal d'amélioration au-delà du bruit, par exemple supérieur à deux écarts-types. Et élargir le dataset dès qu'on plafonne.

Septième piège : le drift d'objectif. Au fil des itérations, le mutateur peut, par dérive insidieuse, optimiser un critère secondaire au détriment du critère principal. Mitigation : figer un critère cible — ce qu'on appelle un primary-metric — dans le manifest, et faire échouer toute itération qui ne déplace pas ce critère dans la bonne direction au-delà du bruit, indépendamment des autres scores.

Huitième et dernier piège : le coût et la latence. Faisons un calcul simple. Le coût d'un run, c'est le nombre de cases multiplié par M répétitions, multiplié par les appels de l'agent — typiquement cinq model calls plus trois tool calls — multiplié par le nombre d'appels du juge, c'est-à-dire un appel par critère par case. Pour cinquante cases, M égal trois, cinq critères, on monte vite à mille-cinq-cents à trois-mille appels LLM par itération. Mitigations : utiliser des cheap models pour le juge quand la rubric est simple — gpt-5-mini est explicitement suggéré par la documentation Pydantic. Mettre du cache sur les outputs déterministes : input identique, on ne re-appelle pas. Faire de l'échantillonnage stratifié : un sous-set rapide pour les itérations exploratoires, le full dataset pour valider une mutation prometteuse. Et imposer une time-box explicite par itération : c'est l'analogue direct du cycle de cinq minutes de Karpathy. Si une mutation prend trop, on l'abort.

Avant de conclure, faisons une comparaison honnête avec AutoResearch et avec DSPy slash GEPA. Avec AutoResearch d'abord. Ce qu'on garde, c'est la mentalité : cent fois plus d'expériences que ce que ferait un humain, le manifest par run, la time-box, l'asset éditable bien circonscrit, l'asymétrie keep-or-discard rigoureuse. Ce qu'on muscle, c'est le métrique — multi-dimensions plus holdout — la stabilité — M runs par case — et la séparation des rôles — le juge n'est pas le mutateur. C'est crucial pour éviter qu'un même agent optimise et s'auto-juge.

Avec DSPy et GEPA maintenant. GEPA partage l'intuition centrale : la réflexion en langage naturel sur la trajectoire bat le scalaire seul. Spécifiquement, GEPA fait trois choses. Premièrement, il maintient une frontière de Pareto de candidats, où chaque candidat domine au moins un autre sur au moins une instance. Deuxièmement, il utilise un reflection-lm — un LLM dédié à la réflexion — qui lit les traces d'exécution plus du textual feedback, pas juste un score, pour proposer la mutation. Troisièmement, il optimise des signature instructions de modules DSPy, dans un cadre très contraint. GEPA réclame entre cent et cinq cents évaluations là où GRPO en RL en demande cinq mille à vingt-cinq mille — c'est un gain documenté de l'ordre de trente-cinq fois.

Ce qui transpose proprement à notre contexte : la réflexion sur trace, pas seulement sur scalaire, qui devient directement notre subagent évaluateur. La frontière de Pareto, qui devient une option sérieuse pour la sélection de mutations multi-critères. Le textual feedback en plus du score, qui devient nos rubrics qui demandent une raison à chaque score. Ce qui ne transpose pas : GEPA suppose que l'asset à muter est un ensemble bien défini de signatures DSPy. Notre asset est plus libre — prompt plus composition de tools — donc l'espace de mutation est plus large et l'optimiseur a moins de structure pour s'aider. GEPA fonctionne dans un cadre où les modules DSPy se composent via des dspy.Predict : la sémantique de tool calls externes, avec leurs side-effects, est moins traitée nativement. Et DSPy est un programming framework, pas un agent framework ; il ne donne pas de gestion d'état multi-turn comme PydanticAI. Conclusion : on vole les principes de GEPA — Pareto, reflection, textual feedback — et on les réimplémente sur l'asset PydanticAI, avec Claude Code dans le rôle de reflection-lm. C'est moins théorisé que GEPA, mais c'est plus flexible.

Pour aller plus loin, quelques pistes que je voulais mentionner avant de conclure. Multi-judges en ensemble : trois modèles différents — un Anthropic, un OpenAI, un open-weights — avec une médiane pour le scoring, et un désaccord notable qui flag un cas à examiner manuellement. Evals contradictoires : un autre subagent essaie de générer des inputs qui cassent l'agent, et ces inputs entrent dans le holdout — c'est analogue à de l'adversarial testing. Datasets synthétiques : Claude Code génère des cas à partir de specs, l'humain valide un échantillon, et les cas validés enrichissent le Dataset. Calibration périodique humaine : tous les N runs, on échantillonne vingt cases et on les fait labelliser par un humain ; on mesure l'agrément juge contre humain ; si l'agrément décroche, on re-prompte le juge. Trajectory diff : une visualisation côte à côte des trajectoires entre run-N et run-N-moins-un pour le même case, qui rend lisibles les régressions silencieuses. Shadow runs en production : injecter une fraction du trafic réel dans le pipeline d'eval, avec PII scrubbing, pour détecter du distribution drift. C'est conforme à la recommandation Anthropic selon laquelle le production monitoring prend le relais après le lancement. Et enfin, branchement vers GEPA : si l'espace de mutation se stabilise sur le système prompt, on peut déléguer cette sous-partie à dspy.GEPA et garder Claude Code pour les mutations de toolset, qui restent plus ouvertes.

Pour conclure, qu'est-ce qu'on commence à coder dès demain si on veut adopter cette approche ? Je propose un point de départ très concret. Étape une, on pose la stack minimale : un agent PydanticAI avec un système prompt et un FunctionToolset propre, l'instrumentation OTel activée via Agent.instrument-all, et un export vers un simple fichier JSON local — pas besoin de Jaeger pour commencer. Étape deux, on construit un Dataset Pydantic Evals avec quinze à vingt cases représentatives — deux ou trois faciles, le reste varié et tagué — plus deux ou trois evaluators : un IsInstance déterministe, un LLMJudge multi-rubric avec température zéro et un modèle différent du modèle de l'agent, et un evaluator custom qui compte les tool calls et flagge les erreurs non récupérées. Étape trois, on écrit un orchestrateur Claude Code qui fait simplement, à la main au début, trois tâches dans cet ordre : lancer un run, lire le rapport, écrire un manifest YAML versionné. Étape quatre, on écrit un mutator Claude Code qui propose une seule mutation argumentée en lisant le manifest précédent, on l'applique, et on relance. Étape cinq, on ajoute le greedy plus regression guard sur un primary-metric figé. Étape six seulement, quand tout marche, on sépare les rôles en quatre subagents distincts. On ajoute le holdout. On ajoute le multi-judge. On ajoute le bootstrap statistique. On ajoute la calibration humaine. Et là, on a une vraie closed-loop, qui hérite de l'esprit AutoResearch, qui muscle ce qu'AutoResearch ne pouvait pas couvrir, et qui ne tombe pas dans les pièges classiques du LLM-as-judge. Le but final, c'est exactement celui de Karpathy : retirer l'humain du chemin critique, et laisser la machine itérer cent fois plus vite qu'elle ne le pourrait avec nous dans la boucle. Mais avec, en plus, la lucidité de savoir que le signal qu'on poursuit est lui-même imparfait, et qu'il faut donc l'instrumenter, le calibrer, et le défier en permanence.
