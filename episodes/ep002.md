# Closed-loop d'évaluation et d'optimisation pour un agent PydanticAI — Rapport de recherche

## Synthèse

L'objet de ce rapport est de fournir au scripteur d'un podcast d'environ 40 minutes la matière première — théorique et pratique — pour décrire une boucle fermée d'évaluation/optimisation appliquée à un agent LLM construit avec **PydanticAI**. La boucle est pilotée par **Claude Code** (subagents) qui joue à la fois l'orchestrateur (lance l'agent), l'instrumenteur (capture la trajectoire via **OpenTelemetry** sans Logfire), l'évaluateur (LLM-as-judge avec rubric, sur fond de **Pydantic Evals**), le réflecteur (analyse) et le mutateur (propose des modifications de prompt **et** de tools, signatures et descriptions comprises).

Le cadre conceptuel est emprunté à **AutoResearch** d'Andrej Karpathy (mars 2026), qui a réalisé un speed-up de 11 % sur nanochat en 700 expériences en 2 jours [[Karpathy 2026]](https://github.com/karpathy/autoresearch). Karpathy isole trois primitives — *editable asset*, *scalar metric*, *time-boxed cycle* — qui se transposent partiellement à un agent LLM. Là où la transposition casse, c'est précisément autour du *scalar metric* : remplacer `val_bpb` (validation bits-per-byte, métrique propre, monotone, peu bruitée) par un score de juge LLM ouvre la porte à toute la pathologie connue des évaluateurs LLM (Goodhart, biais positionnel, biais de longueur, self-preference, instabilité, faux positifs sur petits datasets). On insistera donc sur les mitigations concrètes.

Côté outillage, on appuie sur trois briques :

1. **PydanticAI** comme cadre d'agent (prompt système, `FunctionToolset`, `Tool`, `prepare`, `PreparedToolset`) qui rend le tissu prompt+tools manipulable programmatiquement [[Pydantic Toolsets]](https://pydantic.dev/docs/ai/tools-toolsets/toolsets/).
2. **Pydantic Evals** comme socle de l'évaluation : `Dataset`, `Case`, evaluators (`LLMJudge`, custom), rapport [[Pydantic Evals]](https://pydantic.dev/docs/ai/evals/evals/).
3. **OpenTelemetry SDK + collector OSS local** (Jaeger, Tempo, Phoenix, ou simple `OTLPSpanExporter` vers fichier) pour capturer la trajectoire complète — agent → model call → tool call — afin que Claude Code lise les vraies traces, pas juste l'output final [[OpenInference PydanticAI]](https://arize-ai.github.io/openinference/python/instrumentation/openinference-instrumentation-pydantic-ai/).

On intercale enfin une comparaison honnête avec **DSPy/GEPA** : GEPA partage l'idée de réflexion sur traces et de mutation textuelle pilotée par LLM, mais s'appuie sur une frontière de Pareto et sur un protocole de mutation contraint (signatures de modules DSPy) là où notre boucle Claude-Code-driven est plus libre, plus chère, et plus exposée au reward hacking [[DSPy GEPA]](https://dspy.ai/api/optimizers/GEPA/overview/).

## 1. Pourquoi une closed-loop pour un agent LLM

### 1.1 Les limites des evals one-shot

Les evals one-shot — un input, un output, un score — s'effondrent dès qu'on bascule sur un agent. Anthropic le formule clairement dans *Demystifying evals for AI agents* : « les capacités qui rendent les agents utiles sont aussi celles qui les rendent plus difficiles à évaluer » [[Anthropic 2026]](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents). Trois raisons :

- **Multi-turn et tool use** : un agent enchaîne des appels de modèle et de tools, parfois des dizaines, parfois récursivement. La donnée brute à évaluer n'est plus une chaîne mais un arbre d'événements.
- **Non-déterminisme structurel** : deux runs sur la même tâche peuvent réussir par des chemins différents. Anthropic recommande explicitement « *grade what the agent produced, not the path it took* » et propose deux métriques pour quantifier la variance : `pass@k` (au moins un succès sur k tentatives) et `pass^k` (k succès consécutifs), qui divergent fortement à mesure que k augmente.
- **Le succès partiel existe** : un agent peut réussir 80 % d'une tâche puis dérailler sur la dernière étape. Un score binaire écrase cette information.

### 1.2 La nature trajectoire des agents

Un *agent trace* est, comme le rappellent LangChain et Braintrust, « *a tree of spans where each span represents a step the agent took: a model call, a tool invocation, a sub-agent dispatch, or a retrieval* » [[LangChain Observability]](https://www.langchain.com/articles/agent-observability). Évaluer un agent suppose de capturer puis de raisonner sur cet arbre, pas seulement sur son output terminal. Les frameworks d'observabilité (Phoenix/OpenInference, Braintrust, Langfuse) convergent sur ce point : *trajectory evaluation* = juger la séquence de tool calls, leur ordre, leur pertinence, leur idempotence éventuelle [[Arize Trajectory Evals]](https://arize.com/docs/ax/evaluate/evaluators/trace-and-session-evals/trace-level-evaluations/agent-trajectory-evaluations).

Trois modes sont couramment proposés pour la comparaison de trajectoires :
- **Strict** : mêmes tool calls, même ordre, mêmes arguments.
- **Subset** : pas de tool call superflu par rapport à une référence.
- **Unordered** : bon ensemble de tool calls, ordre libre.

À noter qu'Anthropic met en garde contre la rigidité du mode strict : « *grading very specific steps like a sequence of tool calls in the right order* » exclut les solutions valides imprévues. La trajectoire sert plus à **diagnostiquer** qu'à **noter**.

### 1.3 La motivation Karpathy : itérer 100x plus vite

C'est la raison-mère d'une *closed-loop*. Karpathy en mars 2026 : « *To get the most out of the tools that have become available now, you have to remove yourself as the bottleneck* » [[Winbuzzer 2026]](https://winbuzzer.com/2026/03/23/karpathy-humans-bottleneck-ai-research-xcxwbn/). En 2 jours et ~700 expériences, son agent a trouvé ~20 améliorations cumulant un speed-up de 11 % (de 2,02 h à 1,80 h pour atteindre la qualité GPT-2) sur du code que Karpathy lui-même avait déjà optimisé. Tobias Lütke (CEO Shopify) a reproduit l'exercice : 37 expériences nocturnes, +19 % de performance sur un modèle 0,8 B vs son baseline 1,6 B [[Datascience Dojo]](https://datasciencedojo.com/blog/karpathy-autoresearch-explained/).

Le message à transposer : si l'évaluation peut être automatisée et bornée temporellement, l'humain devient le facteur limitant. Pour un agent LLM en production, on parle facilement de dizaines de variations de prompt et de tools à essayer ; les piloter à la main, c'est s'auto-imposer le rôle de goulot.

## 2. AutoResearch : ce qu'on retient et ce qu'on ne peut pas copier-coller

### 2.1 Les trois primitives

AutoResearch tient sur trois fichiers et trois principes [[GitHub Karpathy autoresearch]](https://github.com/karpathy/autoresearch) :

- **Editable asset** : un seul fichier `train.py`. L'agent ne touche qu'à lui — architecture, hyperparamètres, optimizer, batch size : tout est négociable, mais dans un périmètre étroit (≤ 630 lignes pour tenir dans le contexte). Le reste (`prepare.py`, métriques, données) est gelé.
- **Scalar metric** : `val_bpb` — *validation bits per byte*, indépendant de la taille de vocabulaire, monotone, peu bruité, calculé par du code immuable. Lower is better. Un seul nombre par expérience.
- **Time-boxed cycle** : 5 minutes wall-clock, point. ~12 expériences/heure, ~100 par nuit. La time-box force la comparabilité et empêche un run pathologique de monopoliser le GPU.

Le slogan résume : *one GPU, one file, one metric* [[Datascience Dojo]](https://datasciencedojo.com/blog/karpathy-autoresearch-explained/).

### 2.2 Ce qui se transpose proprement

| Primitive AutoResearch | Équivalent agent LLM |
|---|---|
| `train.py` (editable asset) | Le couple (system prompt, toolset) — descriptions et signatures incluses |
| `prepare.py` (frozen) | Le `Dataset` Pydantic Evals + les rubrics evaluators (au moins les déterministes) |
| `program.md` (instructions à l'agent) | Le prompt de Claude Code orchestrateur/évaluateur |
| Boucle keep/discard via git | Manifest de runs versionné (git ou JSON/YAML) avec scores |
| 5-minute time-box | Budget par itération : N cas d'eval × M runs (variance), borné en latence/$ |

### 2.3 Ce qui casse à la transposition

Le point crucial — et c'est une bonne moitié de l'angle théorique du podcast.

- **Le scalar metric n'est plus propre.** `val_bpb` est calculé par du code, déterministe, vocab-indépendant. Un score de juge LLM est *non-déterministe*, *biaisé* (positionnel, longueur, self-preference), et lui-même *un agent* qui peut se faire tromper. Pydantic prévient explicitement : « *Non-Deterministic: Same output may receive different scores across runs* » [[Pydantic LLMJudge]](https://pydantic.dev/docs/ai/evals/evaluators/llm-judge/).
- **L'agent est non-déterministe à l'exécution.** AutoResearch peut comparer deux runs de `train.py` parce que l'entraînement est suffisamment stable. Un agent LLM peut emprunter deux trajectoires différentes pour le même input. Il faut donc moyenner sur plusieurs runs (`pass@k`), ce qui multiplie le coût.
- **Goodhart explose plus vite.** Karpathy lui-même reconnaît la limite : « *The method only functions where evaluation reduces to numerical metrics. Research domains involving alignment, interpretability, or subjective judgment remain beyond automation's reach* » [[Winbuzzer 2026]](https://winbuzzer.com/2026/03/23/karpathy-humans-bottleneck-ai-research-xcxwbn/). Quand le métrique est lui-même un LLM, le mutateur peut apprendre à plaire au juge plutôt qu'à résoudre la tâche [[Lilian Weng 2024]](https://lilianweng.github.io/posts/2024-11-28-reward-hacking/).
- **Le coût \$\$\$ n'est pas symétrique.** Un cycle de 5 min sur GPU est un coût bien identifié. Un cycle d'eval LLM = N cas × M runs × (appel agent + appels juge). Vite hors de prix.
- **L'eval set vieillit.** AutoResearch a une métrique gravée dans le marbre. Une rubric d'eval, au contraire, a besoin d'être révisée à mesure que l'agent progresse, sinon on overfitte la rubric.

À retenir : on garde la **forme** (loop autonome, time-box, manifest versionné, scalar metric d'arbitrage final), on muscle la **substance** (multi-métriques, multi-judges, holdout, calibration humaine).

### 3.2 Séparation des rôles Claude Code

On distingue idéalement quatre subagents Claude Code, avec des system prompts distincts :

1. **Runner** : reçoit la version courante (prompt+tools), exécute l'agent PydanticAI sur le `Dataset` Pydantic Evals, sauvegarde inputs/outputs, vérifie que les traces OTel sont bien écrites.
2. **Trace analyzer** : lit les spans bruts (export JSON ou requête au collector), produit un résumé structuré par cas : nombre de tool calls, ordre, arguments, retours, erreurs, durées.
3. **Judge** : applique la rubric multi-critères. Idéalement *différent du modèle de l'agent sous test* (atténuation de la self-preference [[Sigl 2025]](https://www.sebastiansigl.com/blog/llm-judge-biases-and-how-to-fix-them/)). Produit un score par critère + un raisonnement.
4. **Mutator** : reçoit (a) l'historique des runs avec leurs scores et leurs diffs, (b) les analyses de trajectoire et de juge, et propose **une seule** mutation pour le prochain run, justifiée. Une seule, pour préserver l'attribution de l'amélioration.

L'option *single-agent qui fait tout* marche aussi mais brouille les rôles ; on préfère la séparation pour la lisibilité du log d'expériences.

### 3.3 Le store de runs

Chaque run produit un dossier :
```
runs/run-0042/
  manifest.yaml        # version_prompt_id, version_tools_id, dataset_id, scores
  prompt.txt           # snapshot exact
  tools.py             # snapshot exact (ou hash + référence à un store)
  outputs/             # un fichier par case
  traces/              # spans OTel (JSON ou trace_id Jaeger)
  judge_report.json    # sortie LLMJudge + raisonnements
  evaluator_notes.md   # synthèse Claude Code (réflexion)
  diff_vs_parent.md    # ce qui a changé par rapport au run précédent
```

Le `manifest.yaml` est l'analogue du commit git d'AutoResearch. Il rend les comparaisons triviales et permet d'écarter rapidement des branches d'optimisation infructueuses.

## 4. Espaces d'optimisation : prompt **et** tools

C'est la spécificité forte par rapport à un GEPA classique qui se concentre sur les instructions de signatures DSPy. Pour un agent PydanticAI, le tissu manipulable est plus large.

### 4.1 System prompt

Variations canoniques :
- **Rewrites globaux** : ton, persona, longueur, structure (sections numérotées vs prose).
- **Ajout/retrait d'exemples** (few-shot) : avec attention au coût en tokens et au risque d'overfitting au format des exemples.
- **Contraintes explicites** : « *avant tout tool call, formule une hypothèse* », « *si la réponse fait moins de N caractères, vérifie avec le tool X* ».
- **Décomposition** : injecter une chain-of-thought structurée vs laisser l'agent libre.
- **Méta-instructions sur l'utilisation des tools** : ordre préférentiel, tool de fallback, gestion d'erreur.

### 4.2 Descriptions de tools

PydanticAI dérive automatiquement la description d'un tool de sa **docstring**, et les descriptions de paramètres du même docstring (Google/Sphinx/NumPy style auto-détecté) [[Pydantic Tools]](https://ai.pydantic.dev/tools/). On peut aussi forcer une description via `Tool(..., description=...)` ou injecter dynamiquement via `prepare`.

Variations à explorer :
- **Verbosity** : description ultra-courte vs détaillée. Trop courte → l'agent ne sait pas quand l'appeler ; trop longue → token bloat et noise.
- **Exemples in-docstring** : un mini-exemple d'invocation peut radicalement améliorer le taux d'appel correct.
- **Cas d'usage explicite** : « *Use this when the user asks about X but NOT when Y* » désambiguïse souvent mieux qu'une longue description neutre.
- **Ordre des tools dans le toolset** : la position dans le contexte influe (cf. positional bias des LLMs eux-mêmes).
- **Nommage** : `search_documents` vs `retrieve_relevant_docs` vs `query_knowledge_base` — l'écart de comportement n'est pas négligeable.

### 4.3 Signatures

Au-delà du nom et de la description, la signature elle-même est un levier :
- **Types** : `int` vs `Literal["a", "b", "c"]` vs `enum` — contraindre via Pydantic réduit drastiquement les appels invalides.
- **Defaults** : un paramètre avec default est moins « obligatoire » dans la perception du LLM.
- **Required vs optional** : surcharger un tool de paramètres optionnels brouille l'appel.
- **Structure imbriquée** : un seul tool à 8 paramètres vs deux tools à 4 paramètres (split). PydanticAI gère bien des `BaseModel` imbriqués comme paramètre, mais cela alourdit le schéma JSON présenté au modèle.

### 4.4 Composition (ajout / retrait / fusion / split)

Le levier le plus puissant et le plus négligé. PydanticAI offre une API riche [[Pydantic Toolsets]](https://pydantic.dev/docs/ai/tools-toolsets/toolsets/) :

- **`FunctionToolset`** : conteneur de tools, avec `add_function`, `add_tool`, décorateurs `@toolset.tool` / `@toolset.tool_plain`.
- **`CombinedToolset`** : merge plusieurs toolsets.
- **`FilteredToolset`** : filtre dynamique selon le contexte (utile pour montrer un sous-ensemble de tools selon l'étape).
- **`PrefixedToolset`** / **`RenamedToolset`** : namespacing et renommage.
- **`PreparedToolset`** : modifie la liste des `ToolDefinition` avant chaque step (descriptions dynamiques).

Mutations typiques :
- **Ajouter** un tool helper (ex. `validate_format`) qui n'existait pas, parce que le juge a noté plusieurs sorties mal formattées.
- **Retirer** un tool jamais appelé ou systématiquement mal appelé.
- **Fusionner** deux tools redondants (ex. `search_by_id` et `search_by_name` → `search(query: str | int)`).
- **Splitter** un tool trop générique (`do_thing(action: str, payload: dict)`) en plusieurs tools spécialisés et typés.

### 4.5 Budget de mutation par itération

Règle d'hygiène inspirée du A/B testing : **une seule mutation par run** quand on est en phase de diagnostic, plusieurs quand on accepte de perdre l'attribution. Karpathy édite librement `train.py`, mais il a un métrique propre et beaucoup d'expériences ; en LLM eval, le bruit est tel qu'isoler la cause d'un gain est précieux.

## 5. Pydantic Evals comme socle

### 5.1 Les concepts

Trois primitives [[Pydantic Evals]](https://pydantic.dev/docs/ai/evals/evals/) :
- **`Case`** : une unité de test. Champs : `name`, `inputs`, `expected_output` (optionnel), `metadata` (libre, ex. `difficulty`, `tags`), `evaluators` (case-specific).
- **`Dataset`** : collection de `Case` + evaluators globaux + nom.
- **Evaluator** : composant qui produit un score. Renvoie un scalar, un `EvaluationReason(value, reason)`, ou un dict de plusieurs résultats nommés.

```python
from pydantic_evals import Case, Dataset
from pydantic_evals.evaluators import LLMJudge, IsInstance

case = Case(
    name="refund_request",
    inputs={"email": "I want my money back, order #1234"},
    expected_output={"intent": "refund", "order_id": "1234"},
    metadata={"difficulty": "easy", "tag": "support"},
)

dataset = Dataset(
    name="support_intents_v3",
    cases=[case, ...],
    evaluators=[
        IsInstance(type_name="dict"),
        LLMJudge(
            rubric="The intent field correctly identifies the user's request.",
            include_input=True,
            model="anthropic:claude-sonnet-4-6",
        ),
    ],
)

report = dataset.evaluate_sync(my_agent_task)
report.print(include_input=True, include_output=True, include_reasons=True)
```

### 5.2 LLMJudge en détail

Paramètres clés [[Pydantic LLMJudge]](https://pydantic.dev/docs/ai/evals/evaluators/llm-judge/) :
- **`rubric`** : la consigne. Pydantic insiste : *be specific*. Préférer « *Response directly answers the question without hallucination* » à « *Response is good* ».
- **`include_input`** (def. `False`) : injecte l'input original dans le prompt du juge. Indispensable pour RAG / agents.
- **`include_expected_output`** (def. `False`) : pour des comparaisons golden.
- **`model`** : choix explicite (`'openai:gpt-5-mini'` pour cheap, `'anthropic:claude-sonnet-4-6'` pour qualité).
- **`model_settings`** : `ModelSettings(temperature=0.0)` recommandé pour la stabilité.
- **`assertion`** / **`score`** : modes de sortie (booléen pass/fail, score 0–1, ou les deux avec noms personnalisés).

Best practices documentées :
1. Rubrics multi-points plutôt qu'une seule consigne floue.
2. **Plusieurs juges** sur des dimensions différentes (factualité vs ton vs format) plutôt qu'un méga-juge.
3. **Combiner avec des checks déterministes** (`IsInstance`, `Contains`, `Equals`) qui s'exécutent d'abord et fail-fast avant les coûteux appels LLM.
4. **Température 0** systématique côté juge.

### 5.3 Custom evaluators

Pour aller plus loin que les évaluateurs intégrés, on étend `Evaluator`. Pseudo-signature :

```python
from pydantic_evals.evaluators import Evaluator, EvaluatorContext, EvaluationReason

class ToolCallCountEvaluator(Evaluator):
    max_calls: int = 5

    def evaluate(self, ctx: EvaluatorContext) -> EvaluationReason:
        n = len(ctx.metadata.get("tool_calls", []))
        ok = n <= self.max_calls
        return EvaluationReason(
            value=ok,
            reason=f"{n} tool calls (limit {self.max_calls})",
        )
```

Un même evaluator peut renvoyer un dict pour produire **plusieurs** résultats nommés (ex. `accuracy`, `efficiency`, `format_ok`), chacun avec sa raison, qui apparaîtront séparément dans le rapport quand `include_reasons=True`.

### 5.4 Le rapport

`dataset.evaluate_sync()` renvoie un `EvaluationReport` qui contient le détail par case et les agrégats par evaluator. Le `report.print(...)` produit un tableau lisible. Pour la closed-loop on l'écrit aussi en JSON pour que Claude Code mutateur le re-parse au prochain tour.

L'intégration **Logfire est volontairement écartée** (payant) ; on capture les events Pydantic Evals via OTel comme tout le reste — c'est le sens de la prochaine section.

## 6. Capture de la trajectoire avec OpenTelemetry

### 6.1 Pourquoi OTel et pas un wrapper maison

Trois raisons :
- **Standard ouvert** : OTel SDK + collectors OSS multiples (Jaeger, Tempo, Phoenix, ClickHouse via SigNoz). Pas de lock-in.
- **PydanticAI émet déjà des spans OTel structurés** dès qu'on active l'instrumentation [[Pydantic Instrumented]](https://pydantic.dev/docs/ai/api/models/instrumented/).
- **Sémantique GenAI conventionnelle** : versions ≥2 stockent les messages dans `gen_ai.input.messages`, `gen_ai.output.messages`, `gen_ai.system_instructions` (conventions OpenTelemetry GenAI), donc rétrocompatible avec d'autres backends GenAI.

### 6.2 Activation côté PydanticAI

Deux modes [[SigNoz PydanticAI]](https://signoz.io/docs/pydantic-ai-observability/) [[OpenInference]](https://arize-ai.github.io/openinference/python/instrumentation/openinference-instrumentation-pydantic-ai/) :

- **`Agent(instrument=True)`** au cas par cas, ou **`Agent.instrument_all()`** global avant tout appel.
- Instrumentation OpenInference (`openinference-instrumentation-pydantic-ai`) qui ajoute des conventions sémantiques *AI* en plus des conventions GenAI standards.

Paramètres notables d'`InstrumentationSettings` :
- `include_content` (default `True`) : embarque prompts et completions dans les events.
- `version` (1–5) : préférer 5 (gestion correcte des deferrals).
- `event_mode` (`'attributes'` vs `'logs'`, version 1 uniquement).
- `tracer_provider` / `meter_provider` : pour pointer vers ton SDK custom au lieu du global.

### 6.3 Structure d'un span hiérarchique

```
agent_run                                     [span racine]
├─ chat <model>                               [model call 1]
│   ├─ gen_ai.input.messages = [...]
│   ├─ gen_ai.output.messages = [...]
│   └─ gen_ai.usage.input_tokens = 1234
├─ tool_call: search_documents                [tool call 1]
│   ├─ tool.name = "search_documents"
│   ├─ tool.arguments = {"query": "..."}
│   └─ tool.result = "..."
├─ chat <model>                               [model call 2]
└─ tool_call: send_email                      [tool call 2]
```

C'est cette arborescence que le subagent *trace analyzer* doit lire. Concrètement il a deux options :
- **Option A : OTLP vers Jaeger/Tempo local** (Docker Compose, port 16686 UI / 4317 OTLP gRPC). Le trace_id du run est sauvé dans le manifest, et le subagent interroge l'API Jaeger pour récupérer les spans.
- **Option B : exporter vers fichier JSON local** via un `SpanExporter` custom ou `ConsoleSpanExporter` redirigé. Plus simple, parfait pour CI et pour un MVP.
- **Option C : Phoenix local** (`http://localhost:6006`) — UI dédiée LLM, lecture des spans depuis SDK Python via API Phoenix [[Arize Phoenix]](https://arize.com/docs/phoenix/tracing/llm-traces).

### 6.4 Mini-snippet d'export local fichier

```python
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.exporter.otlp.proto.http.trace_exporter import OTLPSpanExporter
from pydantic_ai import Agent

provider = TracerProvider()
# OTLP HTTP vers collector local (Jaeger via OTLP receiver, port 4318)
exporter = OTLPSpanExporter(endpoint="http://localhost:4318/v1/traces")
provider.add_span_processor(BatchSpanProcessor(exporter))
trace.set_tracer_provider(provider)

Agent.instrument_all()  # tous les agents PydanticAI émettent désormais
```

Pour un setup encore plus minimal : `ConsoleSpanExporter` et un parseur de logs JSON. Tant qu'on a `tool.name`, `tool.arguments`, `tool.result`, `parent_span_id` et `start_time`/`end_time`, on a tout pour reconstruire la trajectoire.

### 6.5 Comment Claude Code lit ces traces

Le *trace analyzer* reçoit en input le trace_id (ou le path JSON) et produit, par cas du dataset, un résumé canonique :

```yaml
case: refund_request
duration_ms: 4321
total_tool_calls: 3
tool_sequence:
  - {name: search_documents, args: {query: "order 1234"}, ok: true, duration_ms: 230}
  - {name: validate_format, args: {...}, ok: true, duration_ms: 12}
  - {name: send_email, args: {...}, ok: false, error: "missing recipient"}
final_output: {...}
flags:
  - "tool error not recovered"
  - "duplicate search_documents call avoided"
```

Ce résumé devient l'input principal du subagent *judge* et du subagent *mutator*. Sans cette étape, la rubric LLMJudge ne juge que l'output final ; avec, elle juge le *processus* — c'est l'apport central de la trajectoire.

## 7. La boucle d'optimisation pilotée par Claude Code

### 7.1 Workflow concret d'une itération

```
1. Lire manifest du run précédent (run-0041) + sa trace + son judge_report.
2. Mutator: générer 1 proposition de mutation argumentée
   (ex. "ajouter exemple in-docstring sur send_email").
3. Appliquer la mutation: produire prompt.txt + tools.py pour run-0042.
4. Runner: lancer le Dataset Pydantic Evals contre la nouvelle version.
   - Pour stabilité: M=3 runs par case, OTel actif.
5. Trace analyzer: produire les résumés trajectoire.
6. Judge (LLMJudge multi-rubrics + custom evaluators):
   produire scores par dimension.
7. Écrire manifest run-0042: scores agrégés, diff, raisonnement.
8. Décider: keep / discard.
9. Itérer.
```

### 7.2 Le prompt du subagent évaluateur (rubric multi-critères)

Une rubric monolithique « *score this output from 1 to 10* » est l'erreur classique. On préfère décomposer :

```
Tu juges la sortie d'un agent de support client.
Évalue indépendamment chaque critère, sur 0–1, avec justification:

1. INTENT_ACCURACY: l'intention détectée correspond-elle à la demande?
2. SLOT_FILLING: tous les slots requis sont-ils extraits correctement?
3. TONE: ton professionnel et empathique?
4. EFFICIENCY: nombre de tool calls raisonnable (<= 5)?
5. ERROR_HANDLING: les erreurs de tools sont-elles récupérées?

Renvoie un JSON: {critère: {score: float, reason: str}}.
N'attribue pas de score global. Pénalise la verbosité inutile.
```

Quelques principes :
- Demander **explicitement** la justification → tracée dans `EvaluationReason.reason`.
- **Pénaliser explicitement la verbosité** dans la rubric — contre-mesure documentée au verbosity bias [[Sigl 2025]](https://www.sebastiansigl.com/blog/llm-judge-biases-and-how-to-fix-them/).
- **Pas de score global** demandé au juge — l'agrégation est faite par l'orchestrateur, pas par le juge (pour éviter que le juge synthétise selon ses propres priors).

### 7.3 Stratégie de sélection de mutation

Plusieurs régimes possibles, du plus simple au plus sophistiqué :

- **Greedy** : on accepte si le score agrégé du nouveau run > précédent. Simple, mais myope.
- **Greedy avec garde-fou regression** : on rejette toute mutation qui dégrade un critère « essentiel » (ex. INTENT_ACCURACY) même si la moyenne progresse. Reproduit l'idée d'Anthropic des *regression evals* à pass-rate quasi-100 % qui protègent du backsliding [[Anthropic 2026]](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents).
- **Pareto** : on garde une frontière de candidats non-dominés sur les K critères. Inspiré directement de GEPA [[DSPy GEPA]](https://dspy.ai/api/optimizers/GEPA/overview/). Plus robuste contre l'optimisation locale, plus coûteux à gérer.
- **Bandit / UCB** : sur-itérer les branches d'optimisation prometteuses. Pertinent si on garde plusieurs lignées (ce que fait GEPA via le merge de variantes).

Pour un MVP : greedy + regression guard est suffisant et lisible. Pareto si on a du budget.

### 7.4 Critères d'arrêt

- **Plateau** : pas d'amélioration > seuil (ex. +1 pt sur le critère cible) sur N itérations consécutives.
- **Budget** : nombre maximal d'itérations, ou \$ max, ou wall-time max (analogue de la time-box AutoResearch, mais à l'échelle de la boucle entière).
- **Saturation** : score cible quasi-100 %. Anthropic rappelle qu'il faut alors construire un eval set plus dur (eval saturation).

### 7.5 Manifest YAML de run

```yaml
run_id: run-0042
parent_run_id: run-0041
timestamp: 2026-05-03T11:42:08Z
mutation:
  type: tool_description
  tool: send_email
  description: "added concrete usage example in docstring"
  diff_path: diff_vs_parent.md
prompt_hash: sha256:abc...
tools_hash: sha256:def...
dataset_id: support_intents_v3
runs_per_case: 3
scores:
  intent_accuracy: {mean: 0.92, var: 0.01}
  slot_filling: {mean: 0.85, var: 0.03}
  tone: {mean: 0.88, var: 0.02}
  efficiency: {mean: 0.95, var: 0.01}
  error_handling: {mean: 0.74, var: 0.06}
aggregate: 0.868
parent_aggregate: 0.851
verdict: KEEP
trace_paths:
  - traces/run-0042/case-001-rep1.json
  - ...
notes: |
  Mutation acceptée. Gain modeste mais cohérent.
  Note: error_handling reste le critère le plus faible — cible suivante.
```

C'est la pierre angulaire. Elle permet à Claude Code de **lire son propre passé** sans avoir à re-parser des traces brutes à chaque itération.

## 8. Pièges et anti-patterns

C'est le bloc qui sauve le podcast d'être un publi-reportage outillage.

### 8.1 Reward hacking et Goodhart

Loi de Goodhart : « *quand une mesure devient une cible, elle cesse d'être une bonne mesure* ». Lilian Weng documente longuement comment l'optimisation contre un proxy LLM-judge dérive : « *using LLMs as graders is an imperfect proxy for oracle reward and can introduce biases (...) which can lead to reward hacking by exploiting these graders* » [[Lilian Weng 2024]](https://lilianweng.github.io/posts/2024-11-28-reward-hacking/) [[Synthesis AI 2025]](https://synthesis.ai/2025/05/08/ai-safety-ii-goodharting-and-reward-hacking/).

Mitigations pratiques :
- **Plusieurs juges** sur dimensions disjointes ; corrélation des dérives = signal.
- **Holdout dataset** que le mutateur **ne voit jamais** [[Evidently AI]](https://www.evidentlyai.com/blog/automated-prompt-optimization). On évalue dessus tous les K runs ; si le score sur le train monte mais sur le holdout chute → overfitting.
- **Déterministe d'abord** : checks déterministes (format, schémas, présence d'éléments factuels) en pré-filtre. Ils sont incorruptibles.
- **Périmètre de mutation borné** : un mutateur libre de tout réécrire trouvera plus vite des hacks.

### 8.2 Biais du juge

Récapitulatif compact, à présenter dans le podcast comme une checklist [[Sigl 2025]](https://www.sebastiansigl.com/blog/llm-judge-biases-and-how-to-fix-them/) [[arXiv positional bias]](https://arxiv.org/html/2406.07791v5) [[arXiv self-preference]](https://arxiv.org/html/2410.21819v1) :

| Biais | Symptôme | Mitigation |
|---|---|---|
| **Positional** | Préfère systématiquement la 1re option (GPT-4) ou la 2e (ChatGPT) | Pairwise twin-call avec swap, ne valider que si stable |
| **Verbosity** | Score haut pour les longues réponses | Pénaliser explicitement dans la rubric ; contraindre la longueur côté agent |
| **Self-preference** | Préfère les sorties de modèles familiers (faible perplexité) | Juge d'un autre vendeur que l'agent sous test |
| **Authority** | Crédibilise les citations, même fabriquées | Reference-guided eval (passer les sources au juge) |
| **Moderation** | Surnote les refus prudents | Calibration humaine sur cas sensibles |

Recommandation transverse : **calibrer périodiquement le juge contre un golden labellé humain**. Pydantic insiste : *« validate against human labels »* [[Pydantic LLMJudge]](https://pydantic.dev/docs/ai/evals/evaluators/llm-judge/).

### 8.3 Métrique scalaire fragile

L'erreur miroir d'AutoResearch : forcer l'agrégation en un seul nombre alors que les critères sont tirés dans des directions différentes. Symptôme : un run gagne 1 pt sur l'agrégat parce qu'il a gagné 5 pt sur la verbosité (longueur réduite) tout en perdant 3 pt sur factualité. Réponse : suivre **toutes** les dimensions et ne décider qu'avec une règle multicritère explicite.

### 8.4 Instabilité d'optimisation prompt

Un même prompt + même input peut donner deux scores différents. Doug Turnbull note les *« hard negatives »* — les 10–20 % difficiles où humains et juges divergent — comme la zone où tout se joue [[Turnbull 2025]](https://softwaredoug.com/blog/2025/11/02/llm-judges-arent-the-shortcut-you-think.html). Mitigations :

- **Plusieurs runs par case** (M=3 minimum) → reporter mean *et* variance.
- **Température 0 côté juge** systématique.
- **Cas seed** (cases déterministes peu ambiguës) pour vérifier qu'au moins là on a 100 % stable. Si non, le pipeline a un bug.

### 8.5 Overfitting au dataset d'eval

Le risque dont parle DeepEval et Evidently AI : on optimise jusqu'à parfait sur 30 cas, on déploie, on découvre que le 31e ne marche pas. Mitigations :

- **Train/validation/holdout split** des cases (typiquement 60/20/20).
- **Croissance du dataset** : le mutateur écrit des cas synthétiques *adversariaux* depuis les modes de défaillance observés ; humain les valide ; ils entrent dans le dataset.
- **Diversité explicite** : tagging par catégorie dans `Case.metadata`, et reporting par catégorie pour repérer une régression locale masquée par la moyenne.

### 8.6 Faux positifs sur petits datasets

Anthropic recommande 20–50 cas pour démarrer, mais avec **ce caveat statistique implicite** : un gain de 2 pt sur 30 cases peut être du bruit. Mitigations :

- **Bootstrap** sur les scores pour produire un intervalle de confiance avant d'accepter une mutation.
- **Seuil minimal d'amélioration** au-delà du bruit (ex. > 2σ).
- **Élargir le dataset** dès qu'on plafonne.

### 8.7 Drift d'objectif

Au fil des itérations, le mutateur peut, par dérive, optimiser un critère secondaire au détriment du critère principal. Mitigation : **figer un critère cible** (`primary_metric`) dans le manifest, et faire échouer toute itération qui ne le déplace pas dans la bonne direction au-delà du bruit.

### 8.8 Coût \$\$\$ et latence

Coût d'un run : (cases) × (M répétitions) × (appel agent : ~5 model calls + 3 tool calls) × (judge : 1 appel par critère par case). Pour 50 cases, M=3, 5 critères, on monte vite à 1500–3000 appels LLM par itération. Mitigations :

- **Cheap models pour le juge** quand la rubric est simple (`gpt-5-mini` est explicitement suggéré [[Pydantic LLMJudge]](https://pydantic.dev/docs/ai/evals/evaluators/llm-judge/)).
- **Cache** sur les outputs déterministes (input identique → ne pas re-appeler).
- **Échantillonnage stratifié** : un sous-set rapide pour les itérations exploratoires, le full dataset pour valider.
- **Time-box explicite** par itération : analogue direct du *5-minute cycle* de Karpathy. Si une mutation prend trop, abort.

## 9. Comparaison honnête avec AutoResearch et DSPy/GEPA

### 9.1 Vs AutoResearch

| Dimension | AutoResearch | Closed-loop agent LLM |
|---|---|---|
| Asset éditable | Un fichier `train.py` | system_prompt + toolset (PydanticAI) |
| Métrique | `val_bpb` scalaire, code immuable | Score multi-critères LLMJudge, non-déterministe |
| Cycle | 5 min wall-clock GPU | Variable, time-box recommandé |
| Détermisme | ~stable | Faible — exige M runs |
| Coût marginal | Connu (GPU-heure) | Variable, exige cap budget |
| Hack de la métrique | Très contraint (code locked) | Risque élevé (juge LLM) |
| Boucle de réflexion | Agent code, garde si meilleur | Sub-agents séparés (run/trace/judge/mutate), garde si pas regression |

**Ce qu'on garde** : la mentalité « 100x plus d'expériences que ce que ferait un humain », le manifest par run, la time-box, l'asset éditable bien circonscrit, l'asymétrie keep/discard rigoureuse.

**Ce qu'on muscle** : le métrique (multi-dimensions + holdout), la stabilité (M runs), la séparation des rôles (le juge n'est pas le mutateur).

### 9.2 Vs DSPy / GEPA

GEPA partage l'intuition centrale : **la réflexion en langage naturel sur la trajectoire bat le scalaire seul** [[DSPy GEPA]](https://dspy.ai/api/optimizers/GEPA/overview/) [[GEPA GitHub]](https://github.com/gepa-ai/gepa). Spécifiquement, GEPA :

- maintient une **frontière de Pareto** de candidats — chaque candidat domine sur au moins une instance.
- utilise un **`reflection_lm`** qui lit traces d'exécution + textual feedback (pas juste score) pour proposer la mutation.
- optimise des **`signature instructions`** de modules DSPy (très contraint).
- réclame 100–500 évaluations vs 5 000–25 000+ pour GRPO en RL — gain x35 documenté.

**Ce qui transpose** :
- Réflexion sur trace, pas seulement scalaire → directement notre subagent évaluateur.
- Pareto frontier → option sérieuse pour la sélection de mutations multi-critères.
- Textual feedback en plus du score → rubrics qui demandent une *raison*.

**Ce qui ne transpose pas** :
- GEPA suppose que l'asset à muter est un ensemble bien défini de signatures DSPy. Notre asset est plus libre (prompt + composition de tools), donc l'espace de mutation est plus large et l'optimiseur a moins de structure pour s'aider.
- GEPA fonctionne dans un cadre où les modules DSPy se composent via des `dspy.Predict` : la sémantique de tool calls externes (avec side-effects) est moins traitée nativement.
- DSPy est un *programming framework*, pas un agent framework ; il ne donne pas de gestion d'état multi-turn comme PydanticAI.

Conclusion : on **vole les principes** GEPA (Pareto, reflection, textual feedback) et on les **réimplémente** sur l'asset PydanticAI, avec Claude Code dans le rôle de `reflection_lm`. C'est moins théorisé que GEPA mais plus flexible.

## 10. Pour aller plus loin

- **Multi-judges en ensemble** : 3 modèles différents (Anthropic, OpenAI, open-weights), median pour scoring, désaccord = case à examiner manuellement.
- **Evals contradictoires** : un autre subagent essaie de générer des inputs qui *cassent* l'agent, ces inputs entrent dans le holdout — analogue à de l'adversarial testing.
- **Datasets synthétiques** : Claude Code génère des cas à partir de specs ; humain valide un échantillon ; les cas validés enrichissent le `Dataset` [[Anthropic 2026]](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents).
- **Calibration périodique humaine** : tous les N runs, échantillonner 20 cases et faire labelliser par humain ; mesurer l'agrément juge↔humain ; si décroche → re-prompt le juge.
- **Trajectory diff** : visualisation côte à côte des trajectoires entre run-N et run-N-1 pour le même case — rend lisibles les régressions silencieuses.
- **Shadow runs** en production : injecter une fraction du trafic réel dans le pipeline d'eval (avec PII scrubbing) pour détecter du distribution drift, conforme à la recommandation Anthropic *« production monitoring kicks in post-launch »*.
- **Branchement vers GEPA** : si l'espace de mutation se stabilise sur le prompt système, on peut déléguer cette sous-partie à `dspy.GEPA` et garder Claude Code pour les mutations de toolset.
